# PRD: AI·채팅 백엔드

## 1. 배경

웹 기반 AI 챗봇 서비스에서 로그인한 사용자가 질문하고, 이전 대화의 맥락을 반영한 AI 답변을 받을 수 있어야 한다. 질문과 답변은 DB에 저장해 사용자 기준으로 조회·추적할 수 있어야 하며, AI 호출 실패나 타임아웃이 발생해도 오류를 안내하고 서비스를 계속 제공해야 한다.

백엔드는 관리자, 유저, AI·채팅 담당으로 나누어 구현한다. 이 문서는 AI·채팅 담당 범위의 구현 전 초안이다. 인증은 유저 담당자의 기능을 사용하고, 저장한 대화 데이터는 관리자 담당자가 조회 기능에 활용할 수 있도록 구조를 공유한다.

API 요청·응답 계약은 [AI·채팅 API 명세](AI-CHAT-API.md)를 기준으로 한다. 두 문서가 충돌하면 API 명세서를 우선하고, 충돌하지 않는 내부 처리 규칙은 이 PRD를 적용한다. 이 문서의 채팅방은 API 명세서의 세션과 같은 의미다.

## 2. 목표

- 로그인한 사용자가 질문하고 AI 답변을 받을 수 있다.
- 같은 채팅방의 이전 대화를 활용해 문맥을 유지한다.
- 사용자별 질문·응답·시각을 DB에 저장하고 본인 대화를 조회할 수 있다.
- 입력 오류, AI 실패·타임아웃, DB 오류를 처리하고 원인을 로그로 추적할 수 있다.
- 프론트엔드 및 다른 백엔드 담당자가 연동할 수 있는 API와 데이터 구조를 정의한다.

사용자 질문은 앞뒤 공백 제거 후 1~1,000자로 제한한다. 채팅방 단위 대화, 일반 JSON 응답, 최근 5개 질문·응답 활용, AI 호출 타임아웃 30초는 이 초안의 제안이며 팀 협의로 조정할 수 있다.

## 3. 사용자 스토리

### 질문과 답변

- As a 로그인한 사용자,
- I want 채팅방에서 질문하고 이전 대화를 반영한 AI 답변을 받고 싶다.
- So that 대화를 이어가며 필요한 정보를 얻을 수 있다.

### 대화 기록 조회

- As a 로그인한 사용자,
- I want 내 채팅방과 이전 질문·답변을 조회하고 싶다.
- So that 이전에 나눈 대화를 다시 확인할 수 있다.

### 오류 안내

- As a 질문을 전송한 사용자,
- I want 응답 생성에 실패하면 오류 안내를 받고 싶다.
- So that 처리 결과를 이해하고 다시 시도할 수 있다.

- 모델 선택 UI, 결제, 이용량 통계

## 5. 기능 요구사항

- 사용자는 로그인한 상태에서만 채팅 API를 사용할 수 있다.
- 사용자는 본인의 채팅방만 생성·조회·삭제하고 질문을 전송할 수 있다.
- 채팅방 삭제는 `deleted_at`에 UTC 삭제 시각을 기록하는 논리 삭제로 처리한다. 채팅방과 해당 대화 기록은 DB에 유지한다.
- 삭제된 채팅방은 사용자 목록에서 제외하며, 상세 조회·새 질문 전송·재삭제는 `404 CHAT_NOT_FOUND`로 처리한다.
- AI 답변 생성 중이거나 `pending` 기록이 남아 있어도 채팅방 삭제를 허용한다. 삭제 전 소유권·삭제 여부 검사를 통과한 질문 요청은 기존 흐름대로 결과를 저장하고 원래 요청에 성공 또는 오류 응답을 반환한다. 삭제가 AI 호출을 취소하거나 채팅방을 복구하지 않는다.
- 삭제를 위한 Lock·실행 상태 추적·별도 대화 처리 상태는 추가하지 않는다.
- 시스템은 인증 정보에서 사용자 식별자를 가져오며, 요청 본문으로 사용자 식별자를 받지 않는다.
- 시스템은 HTTP 요청마다 서버에서 UUID4 형식의 `request_id`를 생성하고 해당 요청의 모든 처리 로그에서 같은 값을 사용한다.
- 시스템은 질문의 앞뒤 공백을 제거한 뒤 1~1,000자인지 검증한다. 빈 입력·공백만 있는 입력·1,000자 초과 입력은 `422 INVALID_INPUT`으로 거절하며, AI 호출과 대화 기록 생성을 수행하지 않는다.
- 질문 길이는 Python 문자열의 `len()` 기준으로 계산한다. 내부 공백·줄바꿈도 글자 수에 포함하며, 별도 Unicode 정규화는 수행하지 않는다. 조합 이모지 등 화면에서 한 글자로 보이는 문자도 여러 Unicode 코드 포인트로 구성되면 여러 글자로 계산한다.
- 시스템은 AI 호출 전에 질문을 `pending` 상태로 저장하고, 해당 질문 요청의 `request_id`를 대화 기록의 기본키로 사용한다. 답변 저장과 완료·실패 상태 갱신도 같은 `request_id`로 수행한다.
- 시스템은 같은 채팅방의 성공한 최근 5개 질문·응답을 시간순으로 구성하고 현재 질문을 마지막에 추가한다. 다른 사용자·채팅방의 기록과 실패·처리 중 기록은 제외한다.
- AI 입력 한도를 초과하는 경우 가장 오래된 질문·응답 쌍부터 제외하고 현재 질문은 유지한다.
- 시스템은 서버에서 AI API를 호출하고 완성된 답변을 일반 JSON으로 반환한다.
- 시스템은 재시도 대상인 OpenAI 통신 오류에 지수적 백오프를 적용한다. 기본 최대 4회 재시도하며 최초 호출을 포함해 최대 5회 호출한다. 성공하거나 재시도 횟수를 소진하거나 전체 AI 처리 제한 시간이 끝나면 추가 호출을 중단한다.
- 재시도 중에는 같은 질문·대화 문맥과 최초 요청의 `request_id`를 사용하고 기존 대화 기록 한 건을 `pending`으로 유지한다. 질문을 다시 저장하거나 중간 통신 오류를 최종 실패로 기록하지 않는다.
- 시스템은 답변과 `completed` 상태를 저장한 뒤 성공 응답을 반환한다.
- 재시도 소진·재시도 대상이 아닌 AI 오류·전체 AI 처리 시간 초과로 최종 실패한 경우 질문을 유지하고 `failed` 상태와 오류 코드를 저장한다. 답변은 `null`로 두고 사용자에게 기존 공통 오류 응답으로 안내한다. 연결·외부 서비스 실패는 `502 AI_UNAVAILABLE`, 키·모델·권한 오류는 `503 AI_CONFIGURATION_ERROR`, 타임아웃은 `504 AI_TIMEOUT`을 사용한다.
- 질문 저장에 실패한 경우 AI를 호출하지 않는다. 답변 저장에 실패한 경우 성공 응답을 반환하지 않는다.
- DB 오류로 실패 상태까지 저장할 수 없는 경우 서버 로그에 원인을 남기고 저장 오류를 반환한다.
- 같은 채팅방에 처리 중인 질문이 있는 경우 새 질문을 `409`로 거절한다. 동시에 들어온 요청에서도 서버가 하나만 승인해야 한다.
- 사용자는 본인 대화 기록의 질문·답변·상태·시각을 조회할 수 있다.
- 시스템은 요청 수신, AI 호출 시작, AI 응답 수신 또는 실패, DB 저장 성공·실패를 요청 식별자로 연결해 로그에 남긴다.

## 6. API 명세

모든 API에 유저 담당자가 제공하는 인증 의존성을 적용한다. 인증 전달 방식과 사용자 ID 자료형은 유저 담당자의 계약에 맞춘다. 아래 API 및 오류 포맷은 API 명세서를 따른다. 채팅방 식별자 `chat_id`는 UUID이며, UUID 형식이 아닌 경로 매개변수는 `422 INVALID_INPUT`으로 처리한다.

### POST /api/v1/chats

Request:

- 요청 본문 없음

Response:

```json
{
  "chat_id": "e6100748-b7f0-48e6-a264-7c20a748cf93",
  "created_at": "2026-09-30T03:00:00Z"
}
```

Status Codes:

- 201: 채팅방 생성 성공
- 401: 인증 실패
- 500: DB 저장 실패

### GET /api/v1/chats

Request:

- 요청 본문 없음
- 로그인한 사용자의 삭제되지 않은 전체 채팅방 목록 조회

Response:

```json
{
  "items": [
    {
      "chat_id": "e6100748-b7f0-48e6-a264-7c20a748cf93",
      "created_at": "2026-09-30T03:00:00Z"
    }
  ]
}
```

Status Codes:

- 200: 본인 채팅방 목록 조회 성공
- 401: 인증 실패
- 500: DB 조회 실패

### POST /api/v1/chats/{chat_id}/messages

Request:

```json
{
  "question": "FastAPI가 무엇인지 설명해줘."
}
```

Response:

```json
{
  "request_id": "16fd2706-8baf-433b-82eb-8c7fada847da",
  "chat_id": "e6100748-b7f0-48e6-a264-7c20a748cf93",
  "question": "FastAPI가 무엇인지 설명해줘.",
  "answer": "FastAPI는 Python으로 웹 API를 만드는 프레임워크입니다.",
  "status": "completed",
  "error_code": null,
  "created_at": "2026-09-30T03:00:00Z",
  "finished_at": "2026-09-30T03:00:02Z"
}
```

Status Codes:

- 201: 질문·답변 저장 및 반환 성공
- 401: 인증 실패
- 404: 채팅방이 없거나 본인 소유가 아니거나 삭제됨
- 409: 해당 채팅방의 이전 질문이 처리 중
- 422: 질문 입력 또는 UUID 형식 오류
- 500: DB 조회·저장 실패
- 502: AI 연결·외부 서비스 실패 또는 유효한 답변 없음
- 503: AI 키·모델 등 서버 설정 오류
- 504: AI 호출 타임아웃

### GET /api/v1/chats/{chat_id}

Request:

- 요청 본문 없음
- 본인 채팅방 정보와 전체 대화 기록을 함께 조회

Response:

```json
{
  "chat_id": "e6100748-b7f0-48e6-a264-7c20a748cf93",
  "created_at": "2026-09-30T03:00:00Z",
  "messages": [
    {
      "request_id": "16fd2706-8baf-433b-82eb-8c7fada847da",
      "chat_id": "e6100748-b7f0-48e6-a264-7c20a748cf93",
      "question": "FastAPI가 무엇인지 설명해줘.",
      "answer": "FastAPI는 Python으로 웹 API를 만드는 프레임워크입니다.",
      "status": "completed",
      "error_code": null,
      "created_at": "2026-09-30T03:00:00Z",
      "finished_at": "2026-09-30T03:00:02Z"
    }
  ]
}
```

Status Codes:

- 200: 본인 채팅방 정보 및 전체 대화 기록 조회 성공
- 401: 인증 실패
- 404: 채팅방이 없거나 본인 소유가 아니거나 삭제됨
- 422: UUID 형식 오류
- 500: DB 조회 실패

### DELETE /api/v1/chats/{chat_id}

Request:

- 요청 본문 없음
- 본인 소유이며 삭제되지 않은 채팅방의 `chat_id`를 경로로 전달

Response:

- `204 No Content`: 삭제 시각 저장을 완료한 뒤 본문 없이 반환

Status Codes:

- 204: 채팅방 논리 삭제 성공
- 401: 인증 실패
- 404: 채팅방이 없거나 본인 소유가 아니거나 이미 삭제됨 (`CHAT_NOT_FOUND`)
- 422: UUID 형식 오류 (`INVALID_INPUT`)
- 500: DB 조회·저장 실패 (`DB_ERROR`) 또는 예상하지 못한 서버 예외 (`INTERNAL_ERROR`)

삭제는 AI 생성 중에도 허용한다. `pending` 기록이나 실행 중인 AI 요청을 이유로 `409 CHAT_BUSY`를 반환하지 않는다. 삭제 전 소유권·삭제 여부 검사를 통과한 질문은 완료·실패 결과를 기존 대화 기록에 저장하고 원래 요청에 응답한다. 프론트엔드는 삭제된 채팅방의 늦은 질문 응답을 화면에 표시하거나 해당 방을 목록에 다시 추가하지 않는다.

### 공통 조회·오류 규칙

- 채팅방 목록과 상세의 대화 기록은 페이지 조회 없이 전체를 반환한다. `limit`, `offset`, `has_more` 필드는 사용하지 않는다.
- 사용자 채팅방 목록·상세 조회와 새 질문의 소유권 검사는 `deleted_at IS NULL`인 채팅방만 대상으로 한다. 삭제된 방만 남으면 목록은 `{"items": []}`를 반환한다. 삭제 시각은 내부 저장 필드이며 기존 채팅방·대화 기록 응답 필드는 유지한다.
- 채팅방 목록은 `created_at`·`chat_id` 내림차순, 대화 기록은 `created_at`·`request_id` 오름차순으로 조회한다. UUID 자체는 생성 순서를 나타내지 않으므로 시각을 우선 정렬 기준으로 사용한다.
- 채팅방이 없으면 목록 응답은 `{"items": []}`를 반환한다. 본인 채팅방에 대화 기록이 없으면 상세 응답의 `messages`는 빈 배열이다.
- 채팅방 상세의 `messages`에는 처리 중·성공·실패 기록을 모두 포함한다.
- `messages`의 항목 하나는 질문 1개와 답변 최대 1개로 구성된 대화 기록이다.
- 대화 기록의 모든 필드를 응답에 포함한다. `pending`의 `answer`, `error_code`, `finished_at`은 `null`이며, `completed`의 `error_code`는 `null`이다. `failed`의 `answer`는 `null`이고 `error_code`와 `finished_at`은 실패 코드와 실패 시각이다.
- 대화 기록의 `request_id`는 최초 질문 요청의 값으로 유지한다. 기록 조회 요청에는 새로운 `request_id`를 생성하되, 응답의 대화 기록에는 저장된 최초 질문의 `request_id`를 반환한다.
- 시각은 UTC 기준 ISO 8601 형식으로 반환한다.
- 오류 응답은 다음 형식을 사용한다. `request_id`로 해당 요청의 서버 로그를 추적하고, 질문이 저장된 경우 같은 값으로 대화 기록도 식별한다. 입력 검증에서 거절되거나 질문 저장에 실패하면 대화 기록이 없을 수 있다.

```json
{
  "error": {
    "code": "AI_TIMEOUT",
    "message": "응답이 지연되고 있습니다. 잠시 후 다시 시도해 주세요.",
    "request_id": "16fd2706-8baf-433b-82eb-8c7fada847da"
  }
}
```

오류 코드는 상황에 따라 `UNAUTHORIZED`, `CHAT_NOT_FOUND`, `CHAT_BUSY`, `INVALID_INPUT`, `DB_ERROR`, `AI_UNAVAILABLE`, `AI_CONFIGURATION_ERROR`, `AI_TIMEOUT`을 사용한다.

## 7. 기술 요구사항

- FastAPI를 사용한다.
- API는 `/api/v1` 아래에 구성한다.
- 비즈니스 로직과 AI 호출·문맥 구성·소유권 검증은 Service 계층에서 처리한다.
- DB 접근은 Repository 계층에서 처리한다.
- 요청/응답 모델은 Pydantic으로 정의한다.
- SQLAlchemy 비동기 세션과 SQLite를 사용한다.
- 서버의 OpenAI SDK를 사용해 AI API를 호출한다.
- `OPENAI_API_KEY`, `OPENAI_MODEL`은 환경변수로 관리한다. `AI_TIMEOUT_SECONDS`는 기본 30초이며 SDK의 네트워크 타임아웃과 재시도 대기를 포함한 전체 AI 처리 제한에 같은 값을 적용한다. 전체 제한은 AI 호출 시작부터 계산하며 앞뒤 DB 조회·저장 시간은 포함하지 않는다.
- `AI_MAX_RETRIES`는 최초 호출 이후의 최대 재시도 횟수이며 기본값은 4다. 0 이상의 정수만 허용하고 0이면 애플리케이션의 자동 재시도를 비활성화한다.
- AI 키·모델이 빈 문자열이거나 공백뿐이면 설정 검증에 실패하여 서버 시작을 중단한다. 실제 AI 호출에서 확인되는 키·모델·권한 오류는 기존 `503 AI_CONFIGURATION_ERROR`로 처리한다.
- AI 클라이언트는 앱 시작 시 한 번 생성하여 요청 간 재사용하고 앱 종료 시 HTTP 자원을 정리한다. 클라이언트 생성·종료에 실패해도 DB 엔진을 정리한다.
- `.env`는 Git에서 제외하고 `.env.example`과 실행 문서에 설정 방법을 제공한다.
- DB 트랜잭션은 AI 응답을 기다리는 동안 열어두지 않는다. 질문 저장과 완료·실패 갱신을 각각 처리한다.
- 재시도 대상 판단·반복 호출·지수적 대기 시간 계산·지터·서버 대기 지시 처리는 `AIClient`에서 직접 구현한다. OpenAI SDK는 `max_retries=0`으로 고정하여 중첩 재시도를 방지한다. 별도 재시도 라이브러리는 추가하지 않는다.
- 재시도 대상은 SDK가 전달한 네트워크 연결 오류·네트워크 타임아웃 및 OpenAI의 HTTP 408·409·429·5xx 오류다. 그 외 HTTP 오류·빈 답변·미완성 답변·유효하지 않은 응답 형식·예상하지 못한 애플리케이션 예외는 재시도하지 않고 기존 오류 처리로 전달한다. 우리 서버의 HTTP 요청이나 DB 저장 작업을 재전송하지 않는다.
- 첫 재시도를 0번으로 하는 `retry_index`에 대해 기본 대기 시간을 `min(1.0 * 2 ** retry_index, 8.0)`초로 계산한다. 기본 4회 재시도의 대기는 1초 → 2초 → 4초 → 8초이며 재시도 횟수를 늘려도 기본 대기는 최대 8초다. 각 백오프 단계에서 0.75~1.0 범위의 새로운 무작위 배율을 곱하여 지터를 적용한다. 실제 대기는 `asyncio.sleep()`으로 수행한다.
- 서버 대기 지시는 `Retry-After`의 초 단위 숫자만 해석한다. 소수를 포함한 양의 유한 값은 지수적 대기 대신 그대로 사용하며 지터를 적용하지 않는다. 지정된 시간보다 일찍 재시도하지 않는다. `retry-after-ms`와 HTTP 날짜 형식은 지원하지 않는다. `Retry-After`가 없거나 숫자가 아니거나 0 이하·무한대·NaN이면 지수적 백오프와 지터로 대기 시간을 계산한다.
- OpenAI 응답의 `x-should-retry: false`는 재시도 대상 상태 코드에서도 추가 호출을 중단한다. 그 외 헤더 값만으로 재시도 대상이 아닌 오류를 재시도하지 않는다.
- 전체 AI 처리 제한은 기존 `asyncio.timeout()`으로 적용하여 모든 호출과 재시도 대기를 포함한다. 다음 대기 시간이 남은 전체 시간 이상이면 추가 호출 없이 `AI_TIMEOUT`으로 종료한다. 호출 또는 대기 중 전체 시간이 초과되어도 같은 오류로 종료한다. 첫 호출이 전체 제한 시간을 사용한 경우 재시도 횟수가 남아 있어도 추가 호출하지 않는다. 비동기 작업 취소 시 추가 재시도하지 않는다.
- 지수적 백오프·지터·서버 대기 시간 존중 및 중첩 재시도 방지의 참고 자료는 [OpenAI 재시도 안내](https://developers.openai.com/api/docs/guides/rate-limits)다. 구체적인 횟수·시간·오류 응답 계약은 이 PRD의 정책을 따른다.
- 서버 로그에는 `request_id`, 사용자·채팅방 식별자, 처리 결과와 오류 코드를 남긴다. AI 처리 시간도 기록한다.
- API 키·인증 정보·질문·답변 원문은 일반 서버 로그에 출력하지 않는다. 외부 API 원본 오류나 스택 트레이스는 사용자에게 반환하지 않는다.
- 사용자 모델·인증 의존성은 유저 담당자와, 관리자 조회에 필요한 데이터 구조는 관리자 담당자와 합의한다.
- 서버 중단 후 남은 `pending` 기록의 정리와 계정 삭제 시 대화 데이터 처리 정책은 구현 전에 팀과 합의한다.

DB 구조는 다음을 기준으로 한다. 사용자 외래키의 대상과 자료형은 유저 담당자의 모델에 맞춘다.

| 테이블 | 필드 | 용도 |
| --- | --- | --- |
| `chats` | `chat_id`, `user_id`, `created_at`, `deleted_at` | 채팅방 및 소유자·논리 삭제 관리 |
| `chat_logs` | `request_id`, `chat_id`, `question`, `answer`, `status`, `error_code`, `model`, `created_at`, `finished_at` | 질문·응답 및 처리 상태 저장 |

- 사용자 1명은 여러 채팅방을, 채팅방 1개는 여러 대화 기록을 가진다.
- `chats.user_id`는 `Integer`·`ForeignKey("users.id")`로 정의한다. 회원 담당자의 기존 `User` 모델을 사용하며 로그인용 `username`과 정수 사용자 기본키를 구분한다.
- `chats.chat_id`는 UUID 기본키이며, `chat_logs.chat_id`는 해당 채팅방을 참조한다.
- `chats.deleted_at`은 nullable한 UTC 시각이다. `null`이면 삭제되지 않은 방, 값이 있으면 삭제된 방이다. 별도 `is_deleted` 컬럼이나 대화 기록의 삭제 상태는 추가하지 않는다.
- 삭제 시 `chats`와 `chat_logs` 행을 유지하며 기존 외래키를 변경하지 않는다.
- `chat_logs.request_id`는 UUID4 기본키이며, 질문 요청 하나당 대화 기록 하나를 생성한다. 별도 대화 기록 ID는 두지 않는다.
- 사용자 기준 조회는 `chat_logs`와 `chats`를 연결하고 `chats.user_id`와 `chats.deleted_at IS NULL`로 필터링한다.
- `status`는 `pending`, `completed`, `failed` 중 하나다.
- 처리 중·실패 상태의 `answer`는 `null`이며, 처리 중의 `finished_at`은 `null`이다.
- `user_id` 및 채팅방별 기록 조회에 필요한 인덱스를 구성한다.

### 구현 전 확인할 계약·정책

- 서버 중단 후 남은 `pending` 기록의 정리 시점·조건·실패 코드는 팀 합의 후 정한다. 처리 중인 정상 요청을 정리 대상으로 판단하지 않도록 기준이 필요하다.
- 계정 삭제 시 채팅방·대화 기록을 삭제할지 유지할지, 외래키의 삭제 동작은 팀 합의 후 정한다. 정책 확정 전에는 자동 삭제를 설정하지 않고 외래키의 기본 참조 무결성을 유지한다.
- AI 입력 한도에 맞춘 문맥 축소를 위해 입력 토큰 예산과 토큰 계산 방식을 정한다. 현재 질문을 유지한 상태로도 한도를 넘는 경우의 처리 규칙은 PRD에 추가할 필요가 있다.

- [x] 기본 대기 1초 → 2초 → 4초 → 8초와 최대 8초 상한, 각 단계의 새 지터 배율·0.75~1.0 범위를 검증한다. 재시도 횟수를 소진한 뒤 불필요한 대기나 호출이 없는지 확인한다.

- [x] `Retry-After`의 양의 유한 초 값·소수 해석과 미지원 형식·잘못된 값의 백오프 대체, 재시도 금지 지시를 확인한다. 지원하는 서버 대기 초 값보다 일찍 재시도하지 않는다.
- [x] 다음 대기를 남은 시간 안에 완료할 수 없거나 호출·대기 중 전체 시간이 초과되면 추가 호출 없이 `504 AI_TIMEOUT`과 `failed` 기록을 남기는지 확인한다. 비동기 작업 취소 후에도 추가 호출이 없는지 확인한다.

- [ ] UUID형 `chat_id`를 사용하는 채팅방 목록과 상세 조회에서 전체 기록 및 정렬 순서를 확인하고, 서버 재시작 후에도 기록이 남는다.

- [ ] 질문 요청의 UUID4 `request_id`가 대화 기록의 기본키로 사용되고 답변·상태 갱신 및 재조회 후에도 유지된다.
- [ ] API 요청·응답, DB 구조, 환경변수·실행 방법, 개인 작업 요약을 문서화한다.

## 공통 HTTP 오류 연동

- 최신 main의 공통 처리에 따라 없는 API 경로는 `404 NOT_FOUND`, 허용하지 않는 메서드는 `405 METHOD_NOT_ALLOWED`, 그 외 일반 HTTP 오류는 `HTTP_ERROR`를 반환한다.
- 처리하지 못한 서버 예외는 `500 INTERNAL_ERROR`로 반환하며 DB 오류인 `DB_ERROR`와 구분한다.
- 위 오류도 기존 `error.code`·`error.message`·`error.request_id` 구조를 사용한다. 채팅 API의 소유권 오류·인증·입력·AI 오류 코드는 기존 계약을 유지한다.
